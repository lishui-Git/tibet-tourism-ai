## 体例说明

- **只追加，不覆盖**：新记录一律追加到文件末尾，历史记录不得修改或删除。
- **只记真实**：仅记录实际完成并实际验证过的内容；未做完、没测试过的一律不写。
- **无开发则不写**：当天没有实际开发就不产生记录，不为了"保持连续"而虚构。
- **不写论文**：以真实、简洁、可追溯为原则，不追求篇幅。
- **每条记录的结构**：日期 / 本次完成任务 / 修改新增文件 / 主要技术实现或决策 / 测试结果 / 遇到的问题及解决方式 / 当前未解决 / 下一步计划。

**主要技术决策**

1. **数据集口径定稿**：统一表述为「**西藏及进藏沿线（川藏/滇藏/青藏线）旅游景点评论数据集**」。依据：实测西藏口径 554 景点 / 31,752 条，进藏沿线 283 景点 / 27,281 条，合计 837 景点 / 59,033 条。
2. **技术路线定稿（指导老师确认）**：Python 数据清洗 + Spark 离线分析 + DeepSeek 智能评价与总结，**不做实时分析**。据此**移除** Flume / Kafka / Spark Streaming 方案（原因：数据为历史评论静态快照，无实时数据源，引入流式计算无业务价值）。
3. **Python 与 Spark 职责边界**：Python 负责行级清洗、字段规范化、文本预处理、DeepSeek API 调用；Spark（Scala）负责全量多维聚合、MLlib 情感模型训练与批量推理、LDA 主题发现；两者通过 MySQL 衔接，职责不重叠。
4. **景点智能评价门槛**：≥100 条评论的 **57 个景点**（覆盖 50,562 条，占 85.7%）做完整智能评价；<100 条只做基础统计，不做完整评价（因 837 个景点中 568 个不足 10 条、中位数仅 5 条）。
5. **客源地分析口径**：实测 IP 归属地在 2015–2021 年 **100% 为"未知"**（携程自 2022-08 起才展示 IP），故客源地分析**硬编码限定 `发布时间 ≥ 2022-08-01`**（有效样本 35,098 条，其中未知仅 1.5%）。
6. **前端与模型接入定稿**：前端 HTML + ECharts（不引入 Vue 构建链）；DeepSeek 使用**官方 API**，批处理落库，不逐条在线调用。

**遇到的问题及解决方式**

1. **`zip(records, reviews_raw)` 存在字段错位风险**：`build_reviews` 会跳过解析异常的行，一旦发生跳过，按位置对齐就会把景点名配到错误的评论上，且不会报错。**解决**：改为按 `comment_id` 建立映射，并在构建前后显式校验长度一致，不一致则直接终止（宁可失败也不产出错位数据）。
2. **复核脚本第 3 项性能缺陷（导致执行超时）**：最初对 59,033 行**每行都重新遍历该景点全部行**重算代表值，等于重复计算数百万次，脚本连续两次被中断。**解决**：代表值改为**按景点预计算一次**，耗时降到 2.4 秒（同一个脚本、同一套校验口径）。
3. **报告的日期范围一度是「造」出来的**：原实现由年份拼 `f"{year}-01-01"`／`f"{year}-12-31"`，输出成 `2015-01-01 ~ 2026-12-31`，与真实范围 `2015-06-19 ~ 2026-09-16` 不符——这与本项目「不造数」原则直接冲突。**解决**：改为取真实 `publish_date` 的极值，并全量重跑复核确认其他口径未被破坏。

**遇到的问题及解决方式**

1. **清洗版 CSV 列错位（最严重，会静默产生错误结果）**：Spark 读 CSV 用的 schema 只有 19 列，而实际文件有 23 列（漏了"地址/开放时间/官方电话/景点介绍"）。Spark 不报错，只是把后面的列整体左移读取——`is_low_info` 实际读到了 `publish_month`、`is_dup_content` 读到了 `dup_group_id`，后果是"建模输入行数为 0"。**解决**：把 schema 补齐为 23 列并逐列对应；**并新增表头逐列校验**，列数或顺序不符立即终止。定位方式：把诊断结果写入 UTF-8 文件（Windows 控制台按 GBK 解码会丢中文），打印真实 schema 与各标记列的取值分布。
2. **小样本语料过窄导致词表为空**：`--limit` 原按顺序取前 N 行，而 CSV 按景点聚集（200 行只覆盖 7 个景点），`minDF=2` 下词表为空、下游 TF-IDF 直接失败。**解决**：改为**随机抽样（固定种子 42）**，并在词表为空时自动降级 `minDF=1` 且打印提示。
3. **MySQL 驱动把 `TINYINT(1)` 映射为 boolean**：`--source mysql` 时报 `coalesce(is_low_info, 0)` 类型不匹配（`[boolean, int]`）。**解决**：在 MySQL 读取分支显式 `cast(IntegerType)`，使两条数据源类型完全一致。
4. **jieba 不在 executor 类路径 / `--jars` 多 jar 不稳定**：`--driver-class-path` 只覆盖 driver，任务执行用独立 classloader，报 `NoClassDefFoundError: com/huaban/analysis/jieba/JiebaSegmenter`；改为 `--jars` 传两个 jar 又报 `java.io.IOException: Invalid argument`（且本地 `.m2` 路径含中文）。**解决**：用 maven-shade-plugin 把 jieba（约 2 MB）直接 shade 进作业 jar，`--jars` 只保留 MySQL 驱动一个条目。
5. **Spark 3.3.1 与新版文档的 API 差异（照抄新版文档会编译/运行失败）**：① `argmax` 是 3.4+ 的内置函数 → 改用 UDF 求主导主题；② `describeTopics` 返回的是 `termIndices` 而非 `terms`，且 `LDAModel` 没有 `vocabulary` 属性 → 词表由 `CountVectorizerModel` 传入；③ Spark 返回的数组列运行时是 `mutable.ArraySeq`，而 Scala 2.13 的 `Seq` 是 `immutable.Seq`，强转抛 `ClassCastException` → 加取值辅助函数兼容。
6. **`BIGINT UNSIGNED` 经 JDBC 取回是 `BigDecimal`**：直接 `getAs[Long]` 抛 `ClassCastException`，导致 `sentiment` 写库中断。**解决**：新增 `Db.toLong/toInt` 兼容转换。
7. **`executeBatch` 返回 `SUCCESS_NO_INFO(-2)` 导致写入计数显示为 0**：数据实际已写入，但日志打印"已写入 0 行"，极易误判为写库失败。**解决**：把 -2 计入成功数（实测确认 `stat_spot` 837 行确已写入）。
8. **`Db.queryRows` 的值是 `Option` 包装**：`_.get("spot_name").toString` 得到字符串 `"Some(布达拉宫)"`，用它去 filter 匹配 0 行，导致**景点级 LDA 产出 0 个主题**。**解决**：解包后再用（加诊断日志后定位，52/57 个景点恢复产出）。
9. **Windows/Git 环境类问题**：① PowerShell 5.1 按 GBK 读取无 BOM 的 `.ps1`，中文注释直接导致解析失败 → 两个 `.ps1` 改为**纯 ASCII**；② pom.xml 的 XML 注释中不能出现连续两个连字符，`--jars`/`--class` 字样会使 POM 无法解析 → 改写措辞；③ 控制台按 GBK 解码 Spark 输出会丢中文 → 诊断输出改写 UTF-8 文件。

**主要技术实现或技术决策**

1. **"事实"与"解释"分离（BR-07 的工程落地）**：C-BAT-06 的事实包全部由 SQL 聚合（或读取 Spark 已验证的 `stat_spot`），
   DeepSeek 只在 C-BAT-07 里负责语言组织；模型无法改数，数字一致性校验（误差 > 0.5 个百分点 → `need_review=1`）兜底。
2. **evidence 必须是原文子串（§15.A.4 第 5 条）**：模型给出的方面证据若无法在评论原文中定位，说明它在编造，
   该方面**直接弃用**（`dropped_aspects` 计数留痕）。这是"数据负责事实"在单条评论粒度的强制关卡。
3. **分层顺序即优先级**：低信息量（≤10 字）优先走规则判定（BR-05），因此"既重复又低信息量"的评论不会触发调用；
   重复组内若存在非低信息量成员，则由它作为代表调用一次，其余成员复用结果（BR-06）。
4. **代表评论口径三处一致**：SQL 取候选、SQL 取复用成员、Python 端辅助函数都使用同一排序键
   （`is_low_info ASC, content_length DESC, comment_id ASC`）——口径漂移会导致"代表被漏掉 → 整组无结果"，
   本阶段实际踩到过该问题（见"遇到的问题"第 3 条）。
5. **幂等键选在结果表自身**：断点游标 = `sentiment` 中已存在 `method='deepseek'` 的 `comment_id`，
   不引入额外状态文件，避免"状态说成功但数据没写进去"的不一致；重跑不重复计费。
6. **`aspect` 采用"先删后插"**：方面行的数量会随重跑变化（模型可能给出不同方面数），
   仅靠 upsert 会残留旧方面，因此按 `comment_id` 先删再插。
7. **Prompt 版本可追溯**：`SEMANTIC_PROMPT_VERSION` 写入 `sentiment.raw_json.prompt_version`，
   `REPORT_PROMPT_VERSION` 写入 `spot_report.prompt_version`；模板改动必须递增版本号。
8. **安全闸门写进代码**：`--mock` 只允许 `--limit ≤ 50`；未指定 `--limit` 的真实全量必须显式 `--yes`，
   防止"少写一个参数"就触发 4.7 万次调用。

**遇到的问题及解决方式**

1. **设计文档对 C-BAT-05 的工作量分配偏乐观（如实修正，未调口径）**：§7.4 与流程图按
   "59,033 − 10,228 − 4,239 ≈ 44,565 次"估算调用量，但重复正文组内**仍需各调 1 次代表**；
   实测为 **47,733 次**（多 3,168 次 / +7.1%），仍在"≤45,000 口径"的量级内。
   已在本阶段文档中如实记录差异原因，未为了贴合估算而改动分层策略。
2. **`--limit` 语义错误（会破坏幂等）**：原实现先取前 N 条候选再过滤"已处理"，
   导致带 `--limit` 重跑时处理的不是同一批数据。**解决**：把"已有 deepseek 结果"的过滤下沉到 SQL，
   `--limit` 只截断"需要调用模型"的部分；小样本因此也能顺带验证规则层与复用层。
3. **重复组代表被漏掉（BR-06 失效，最严重）**：代表评论本身也带 `is_dup_content=1`，
   而候选 SQL 当时用 `is_dup_content = 0` 过滤，导致代表从未进入调用层 → 整组都没有结果。
   **解决**：候选 SQL 改为"非重复 或 是本组代表"，并用窗口函数 `ROW_NUMBER()` 统一代表口径（三处一致）。
4. **复用层重复写同一行导致统计虚高**：调用层之后再补一次复用（此时本轮新产生的代表结果才可用），
   第二次会把第一次已写的成员再写一遍。全量压测暴露为"写入计数 60,889 ≠ 实际 59,032 行"。
   **解决**：复用前先排除已写入的成员，并把两次复用的写入量正确累加；修正后 59,006 = 库内实际新增。
5. **`spot.intro` 列名不存在**：事实包取景点介绍时用了设计文档里的简称，实际列名是 `introduction`
   （§15.B 的 JSON 字段名是 `intro_excerpt`，与数据库列名不同）。**解决**：按建表脚本实际列名读取，
   仍以 `intro_excerpt` 写入事实包 JSON。
6. **mock 客户端并发下失败注入次数不可预期**：计数未加锁，并发调用会丢计数（实测 6 条候选注入了 4 次失败）。
   **解决**：给计数器加 `threading.Lock`，使"每 N 次失败一次"在并发下仍然确定。
7. **`--mock` 且不传 `--limit` 时会写满全库假数据**：第一次运行验证脚本时未限制样本，
   对 5.9 万条评论执行了 mock 分析（已全部清理）。**解决**：在 CLI 中加安全闸门
   （`--mock` 必须带 `--limit ≤ 50`），并在验证脚本中改为"只处理显式指定的少量评论 + 精确清理"。

**遇到的问题及解决方式**

1. **`--only-ids` 被规模闸门拦住（安全性/可用性缺陷）**：该参数是"指定若干评论"的显式枚举，
   规模由用户写死，不存在"误触发全量"的风险；但闸门按"未指定 `--limit` 即视为全量"拒绝执行，
   导致 README 里写的**失败补跑方法实际不可用**。**解决**：闸门识别 `--only-ids` / `--spot-ids` 直接放行。
2. **`raw_json` 名不副实（可追溯性缺陷）**：该列注释为"模型原始返回（便于复核与复现）"，
   但实现只写了校验后的结构化结果，**模型原文没有留档**，事后无法判断"模型当时编了什么"。
   **解决**：新增 `model_raw` 字段；同时把 `dropped_aspects` 由计数改为**明细**（方面名＋模型给的证据＋丢弃原因）。
3. **token 用量未落库（成本不可审计）**：`usage` 只存在于进程内存，事后仅凭数据库无法复核费用。
   **解决**：`usage` 写入 `raw_json`；复用行的 `usage` 记 0，便于核算时区分"真实调用"与"复用"。
4. **验证脚本会误删真实数据（风险操作）**：脚本原本假定结果表为空，且按 comment_id 删除，
   在有真实结果的库上运行会连带删除真实行（实测发生过）。**解决**：改为运行前拍快照、只删"快照之后新增的 ID"；
   清理后断言"回到快照规模"，实测 34/34 通过且真实结果零损失。
5. **`--limit` 的行为容易被误解为"重复处理同一批"**：它实际是"处理接下来的 N 条待处理数据"
   （断点续跑应有的语义，避免漏数据），因此重跑会继续往后推进并产生真实费用。
   **解决**：在无待处理数据时打印明确提示，并在 README 写明"验证幂等请用 `--only-ids`"。
6. **模型确实会编造 evidence（实测证据）**：4 批共 **20 个方面**被 `evidence 必须是原文子串` 规则拦下，
   例如「青藏公路美翻了」在原文中并不存在。**结论**：该强制校验不是形式主义，
   已把被拦下的证据与原因留档在 `raw_json.dropped_aspects`，可作为论文中"模型幻觉"的实证素材。

   §15.D.3 的"解读失败降级"完全一致，**一条路径两种用途**（省成本 / 失败兜底）。
3. **情感口径不混用**：对比只用 `method=deepseek`；某侧没有 deepseek 结果时返回 `null`，
