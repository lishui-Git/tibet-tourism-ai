# 毕业设计工作目录（AI 辅助开发规范）

> 本目录为毕业设计项目的全周期工作目录，由 AI 全程辅助开发。
> 用户已授予较高权限，但 AI 必须遵守以下规范，**不得乱动本地文件**。
> 每次会话开始前，先读完本文件再动手。

## 一、项目定位

- **毕业设计题目**：《基于 DeepSeek 的西藏旅游景点智能评价与分析系统的设计与实现》
- **一句话定位**：西藏及进藏沿线（川藏/滇藏/青藏线）旅游景点评论数据的**离线**智能评价与分析系统
- **数据基础**：携程平台采集的旅游评论数据集（59,033 条 / 837 个景点 / 15 字段），数据采集阶段已完成，数据质量已经检查，**教师已认可当前数据规模**

### 技术路线（已定稿，以《项目现状分析.md》结论为准）

| 层 | 技术 | 职责 |
|---|---|---|
| 数据清洗层 | Python | 数据清洗、文本预处理 |
| 离线分析层 | Spark | 离线数据分析（不做实时） |
| 智能评价层 | DeepSeek | 评论语义理解、景点智能评价与总结 |
| 存储层 | MySQL | 数据存储 |
| 后端 | Flask | Web 后端服务 |
| 前端可视化 | ECharts | 数据可视化 |

**注意**：以上为当前已形成的技术路线。**不要**擅自增加 Kafka、Flume、Spark Streaming、Flink、Hadoop 集群等实时计算技术——教师已知晓"数据主要是历史旅游评论，不考虑实时分析"。

`tmp/` 下的模板副本与脚本属工具文件，正式成果以 `开题/` 目录内的文档为准。

**业务需求文档生成方式（可重跑）**：**以 `开题/业务需求文档.md` 为唯一内容源**，`tmp/md2docx.py` 将其转换为 `开题/业务需求文档.docx`。修改需求**只改 .md 再重新生成**，不要直接改 docx；docx 中的目录为 Word 目录域，打开后需右键"更新域"。

**需求文档的约束力（重要）**：`开题/业务需求文档.md` 是后续设计、开发与验收的**基准文档**。**凡文档未列出的功能原则上不实现**；开发中如确需增删需求，**必须先更新该文档并确认**，再动代码，避免出现"开题写了、代码没做"或"代码做了、文档没有"的不一致。

**封面信息约定（必须遵守）**：开题报告的封面字段（**组长、组员、学院、专业、指导教师**）属本人填报内容，**AI 一律不得填写、不得覆盖、不得代填**。生成脚本对配置为 `__KEEP__` 的封面字段必须跳过替换；重新生成文档时，若发现封面已被本人手工修改，**以文档内的现有内容为准，不得用模板值覆盖回去**。如需重新生成，**先确认封面字段与本人已填内容一致**。

**设计文档的约束力（重要）**：`docs/` 下的设计文档是**编码阶段的直接依据**，且已通过 `docs/设计阶段一致性检查报告.md` 的交叉检查。开发时须遵守：

- **C4 组件编号是追溯锚点**：详细设计中每个模块都标注 `C-API-*`／`C-BAT-*`／`C-SPK-*` 编号，**不得实现 C4 中不存在的模块**；如需新增，先更新架构与详细设计。
- **数据库以 `docs/database/建表脚本.sql` 为准**：建表直接执行该脚本，字段名与类型不得随意改动；如需改动先更新数据库设计说明与 ER 图。
- **接口以详细设计 §6.2 为准**：接口路径、参数、错误码、响应结构不得随意变更；`available=false`（数据不足）与 `OUT_OF_SCOPE`（超范围拒答）是**正常业务响应**，不是错误。
- **口径必须集中实现**：客源地仅 2022-08 后、评价门槛 ≥100 条、方面样本 <10 条不出结论等规则，在组件内统一实施，**前端不复写规则**。
- **复查脚本**：`tmp/check_design.py`（文档一致性）、`tmp/check_sql2.py`（SQL 结构）、`tmp/check_tables.py`（表清单）、`tmp/check_flow.py`（流程图节点）、`tmp/check_ghost.py`（失效引用）可随时重跑复验。

## 四、AI 工作守则（必须遵守）

1. **仅在当前毕业设计项目根目录及其子目录内操作**：禁止读写、移动、删除 项目目录之外的任何用户文件；临时文件放本目录下的 `tmp/`，任务结束清理。
2. **先看再改**：修改脚本或文档前必须先读取原文件，理解现有逻辑与命名风格，禁止盲改。
3. **数据文件默认只读**：清洗 / 去重 / 转换一律输出新文件（带版本或日期后缀），保留原始数据（见"数据冻结"）。
4. **删除与覆盖需先确认**：任何删除文件、覆盖已有文件的操作，必须先向用户列出目标并确认；新建文件不受此限。重要数据变更前先备份或版本化。
5. **不安装全局依赖**：优先使用已有环境；如需新依赖，先说明用途并征得同意，尽量使用虚拟环境或项目本地安装。
6. **不留垃圾**：不随意生成临时脚本、日志文件；确需中间产物时集中放入 `tmp/` 并在任务结束后说明。
7. **变动留痕**：每次任务结束在回复中说明新增 / 修改了哪些文件；重要数据变更同步更新对应报告文档。
8. **不执行危险命令**：禁止格式化、递归强删、修改系统配置等任何破坏性命令。
9. **写入成品文档前先探测是否被占用**：`开题/` 下的 .docx 常被 WPS／Word 打开。写入前必须先尝试以独占方式打开目标文件；**若被占用，绝不强制关闭 WPS／Word，也绝不删除 `~$` 锁文件**（会丢失用户未保存的内容），而是先生成到 `tmp/` 预览件并告知用户，待关闭后再落地。生成脚本应支持以环境变量覆盖输出路径（现有：`KAITI_OUT`、`BRD_OUT`、`FIX_OUT`）。
10. **已交付文档用手工改过时，改用"最小改动"方式**：若用户已在文档中手工插入了图片、调整过格式，**不得整篇重新生成**（会冲掉用户的手工内容），而应只替换需要变更的段落，并先检查关系 Id 等标识是否已被占用。
11. **图片／关系类改动的强制检查**：涉及 docx 图片、关系（`rId`）、媒体文件时，**必须先枚举目标文档中已占用的全部 Id 再分配新 Id**，严禁直接复用或追加同名 Id；改完后须核对每张图片的 `rId → media 文件 → 字节数` 与在 Word 中解析出的实际尺寸是否吻合。
9. **诚实汇报**：测试失败就如实说失败；不确定的结论标注不确定，不编造。

## 五、开发流程纪律

### 文档先行

后续开发必须遵循：

**需求分析 → 系统设计 → 数据库设计 → 技术方案 → 编码 → 测试 → 文档同步**

如果某项功能尚未在需求或系统设计中确定，**不要擅自开发大型功能**。不要为了"看起来功能丰富"而自行增加复杂模块。

### 防止过度设计

这是**本科毕业设计**。AI 可以提出优化建议，但不能擅自把项目扩展成复杂的大型系统。以下内容**未经确认一律不得增加**：

- 实时数据流（Kafka / Flume / Spark Streaming / Flink 等）
- 用户画像、个性化推荐
- 复杂 RAG
- 微服务、分布式集群
- 大规模模型训练
- 复杂权限系统
- 不必要的中间件（Redis / Docker / K8s 等）

所有新增功能必须先说明必要性，并**等待用户确认**。

### 技术路线不可擅自改变

如果历史文件、旧提示词（如 Trae 提示词）或其他资料中存在与当前项目不同的技术方案（Kafka、Flume、Spark Streaming、Vue 等），**以当前毕业设计确定的技术路线和最新项目文档为准**，不得把旧方案自动带入。

**资料优先级**（冲突时从高到低）：

1. 当前最终数据及数据质量报告
2. 当前项目现状分析 / 需求设计文档
3. 当前毕业设计题目与教师要求
4. 历史资料 / 旧提示词

## 六、开发日报规则

### 目的

`开发日报/开发日报.md`（及同目录下正式表格版 `开发日报_正式表格版.md`、`开发日报_正式表格版_AI参与.md`）用于记录毕业设计**从当前阶段开始的实际开发过程**，作为过程材料留存。后续导师若要求提交开发日志、过程材料或答辩材料，再根据学校/导师的最终要求另行整理，**这些文件不需要按学校正式格式设计**。

### 规则（AI 必须遵守）

1. **每次实际完成开发任务后**，在 `开发日报/` 下三个文件（Markdown 版 + 两个正式表格版）的**末尾追加**当天记录。
2. **只记录实际完成、实际测试过的内容**，不允许编造开发进度或测试结果。
3. **历史日报只能追加，禁止覆盖或删除已有日报内容**（写入时使用追加方式，禁止重写整个文件）。
4. **如果当天没有实际开发，不需要为了保持连续性而虚构日报**。
5. 日报重点记录：**日期 / 本次完成的任务 / 修改或新增的文件 / 主要技术实现或技术决策 / 测试结果 / 遇到的问题及解决方式 / 当前未解决的问题 / 下一步计划**。
6. 如果本次开发过程中出现**重要的技术决策、方案调整或数据问题**，应在日报中简要记录**原因**。
7. 日报**不需要写成论文**，不要长篇大论，以**真实、简洁、可追溯**为原则。
8. AI 参与开发的情况可以**客观记录**，例如"使用 AI 辅助完成……"，但**不要虚构人工操作或测试过程**。

全部位于 `开发日报/` 目录下：

| 文件 | 形式 | 用途 |

| `开发日报/开发日报_正式表格版.md` | 任务模块 × 日期 表格 | 参照课程项目开发日报样式，便于提交导师；**不体现 AI 辅助** |
| `开发日报/开发日报_正式表格版_AI参与.md` | 同上 | 同上，但**如实记录 AI 辅助情况** |

- 三个文件**记录内容必须一致**，仅呈现形式与 AI 表述不同。
- **同日更新时三个文件都要更新**；每次只在各自末尾追加，禁止覆盖或删除历史内容。
- 表格版的字段口径：**任务模块 / 任务占比 / 任务（预）实现技术 / 日期 / 计划完成 / 已完成 / 未完成 / 开发心得 / 遇到的问题 / 明日计划 / 当日任务完成度 / 任务完成度**。
- **"任务占比""任务完成度"属于主观估算**，必须在表头注明口径（例如：占后续规划工作量的比例），不得让人误读为论文整体进度。
- 表格版中**计划字段（计划完成 / 明日计划）与已完成字段必须严格区分**，未做的事一律写在"未完成"或标注"未开始"。

### 边界说明

- 日报是**过程记录**，不是成果文档；成果性结论仍以 `项目现状分析.md`、后续需求/设计文档为准。
- 未完成的探索、失败的尝试、被否决的方案，如需记录，必须明确标注为"未完成 / 未通过"，不得写成已完成。
- **不得为了提高"任务完成度"而把计划中的任务写成已完成**；宁可不写，不可虚构。
