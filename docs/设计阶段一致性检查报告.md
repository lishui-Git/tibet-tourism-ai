## 8. Spark 与 DeepSeek 职责重叠检查

| 能力 | 承担方 | 是否重叠 |
|---|---|---|
| 全量多维统计聚合 | Spark SQL | 否（DeepSeek 不做数值统计） |
| 情感极性分类（基线） | Spark MLlib | 否（与 DeepSeek 为**基线与主方法**关系，结果并列可对照） |
| 主题发现（LDA） | Spark MLlib | 否（DeepSeek 不产出主题占比） |
| 细粒度语义（方面＋证据） | DeepSeek | 否（MLlib 不做方面级抽取） |
| 自然语言生成 | DeepSeek | 否（Spark 不生成文本） |
| HTTP 调用大模型 | Python（非 Spark） | ✅ 明确：**Spark 容器不发起任何 HTTP 调用** |

**对照答辩问题"MLlib 能做情感分析，为什么还要 DeepSeek"**：详细设计 §4.2 与 C4 容器图 §4.2 均已写明——MLlib 输出整体极性（回答"整体情感如何"），DeepSeek 输出细粒度语义（回答"评论具体在说什么、游客在乎什么"）；二者为**基线与增强**关系，通过对比实验说明差异。

## 16. 未采纳但曾被考虑的设计（留档备查）

| 曾考虑 | 最终决定 | 理由 |
|---|---|---|
| 用 RAG／向量检索做问答 | 采用"结构化检索 ＋ 事实拼装" | 数据是结构化统计而非长文档，SQL 可精确回答数值问题；且无向量库部署条件（ADR-3） |
| 在 Web 请求中实时调用模型生成景点评价 | 改为离线批处理预生成 ＋ 落库 | 响应时间无法满足 ≤3 秒；重复访问会重复计费（ADR-1） |
| 用 Redis 缓存热点查询 | 不引入 | 生成类结果已落库即缓存；单机并发 10–20，MySQL 加索引足够（ADR-5） |
| 单一"评论全字段宽表" | 拆为 `spot` ＋ `review` 及多张结果表 | 语义结果需多方法并列；批处理需部分重跑（ADR-2） |
| 原生 Word 矢量流程图 | 改为本人在绘图网站出图后插入 | Word 拒绝 wps 矢量组 schema（历史记录见开发日报） |
| 保留 `spot_comparison` 对比缓存 | **按要求删除** | 该内容约 900 tokens、低频触发、景点对重复率低，缓存收益有限；已按要求不申请保留 |
