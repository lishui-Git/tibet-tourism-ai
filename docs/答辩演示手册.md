## 五、答辩会被问到的问题与标准回答

**Q1：为什么不是每次用户查询都重新调用大模型？**
> 因为本系统面向旅游评论数据集的**离线智能分析**：DeepSeek 负责离线语义结构化
> （评论语义、景点事实包、景点评价），结果**持久化到数据库**；
> Web 层只负责查询、展示与组合分析结果。
> 这样结果**可复现**、响应**稳定**、模型调用**成本可控**。
> 具体到代码：`app/web/**` 里没有任何 `app.llm` 导入、没有 `requests`、没有硬编码外部地址。
>
> **而且这一点有实测证据**（不只是代码检索）：`scripts/test_readonly_api.py` 会把
> 33 个只读 GET 接口全部请求一遍，然后证明 17 张表的行数**逐表一行未变**，
> 并且**没有新增 `analysis_task` / `task_log`**——即"看页面不会触发任何批处理或模型调用"。
> 答辩时若被追问，可以直接说这个结论及其验证方式。

**Q2：那在线还需要模型吗？需要多少？**
> 只有两个**用户主动触发**的低频场景：景点对比解读、智能问答。
> 它们由 `APP_COMPARE_LIVE` / `APP_QA_LIVE` 控制，**默认关闭**；
> 关闭时接口返回 200 + 数据依据 + 明确原因，并给出 `reached_model=false`。
> 另外问答有**三条根本不进入模型**的分支：超范围直接拒答、未识别到景点则提示补充、
> 检索无数据则如实说明"没有相关信息"——**模型在本系统中没有任何"自己知道答案"的场合**。

**Q3：成本怎么控制？**
> 三层去重与规则前置：① 正文 ≤10 字走**规则层**（10,228 条，零 API）；
> ② 重复正文按组只对**代表样本**调用一次（1,285 组），组内其它评论**复用**结果（1,071 条，零 API）；
> ③ 只有真正需要语义理解的才进模型（47,701 条）。
> 全量预检显示：**47,759 次调用、预计 ¥79.39–103.31**，且**必须显式 `--yes`** 才会执行。
> （`47,759 = 评论级 47,702 + 景点级 57`；事实包 0 次。费用分项与合计在预检里会一并打印，
> 且**分项相加恰好等于合计**，可当场按计算器核对。）

**Q4：数据可靠性怎么保证？**
> 每张结果表都带 `sample_size` 与 `caliber_note`（BR-10）；
> 方面级结论有 **BR-04 门槛**（样本 <10 条不出结论，页面显示"不出结论"而非硬给结论）；
> 评论量 <100 的景点按 BR-02/BR-03 **不生成评价**；
> 预检还校验核心 `spot`/`review` 的**行数与 CRC32** 未被改动。

**Q5：如果模型返回不规范怎么办？**
> 有两道防线：**结构校验**（JSON/枚举/方面候选/证据必须是原文子串——
> 实测 20 个编造的 evidence 方面被拒）与**数字一致性校验**
> （回答中的数字必须能在提供的事实里找到，否则标记 `need_review=1` 待人工复核）。

安全机制（均已实现并验证）：

| 机制 | 实现 |
|---|---|
| 运行前显示调用量与费用 | `--stage preflight`（打印 `ESTIMATED API CALLS` / `ESTIMATED COST`） |
| 无显式确认不调用 | 规模超过阈值必须加 `--yes`，否则拒绝执行 |
| 中途中断可续跑 | 游标 = 结果表中已存在的行；重跑只处理未完成部分 |
| 已成功不重复调用 | `NOT EXISTS(... method='deepseek')` 幂等过滤（31 条已有结果会被跳过） |
| 失败可单独重试 | `--only-ids` / `--spot-ids` 精确重试，绕过规模闸门 |
| 并发不重复请求 | 单次运行内**先切分工作量再并发**，且 `ON DUPLICATE KEY UPDATE` 保证**写库**不重复 |
| **两个实例不会重复扣费** | 同类型任务仍在 `running` 时**拒绝再开一个实例**（否则两边会各自计划出同一批 4.7 万条、**费用翻倍**）；`--dry-run` 与只读阶段不受影响；超过 6 小时的 `running` 视为崩溃遗留、不阻断；确需并行用 `--allow-concurrent` |
| **写库失败不重复扣费** | **只重试写库（≤3 次），绝不重调模型**；仍失败则已付费结果落盘 `logs/recovery/*.jsonl` 待补（`write_records_safely`，见 `app/llm/README.md` §7.1） |
| **已付费结果能补写回库** | `--stage replay [--dry-run]`：把恢复文件写回数据库，**零模型调用**；补写成功才删除凭证（`scripts/test_replay.py` 16 项验证往返） |
| 事实包零调用 | `--stage facts` 为纯 SQL 聚合，源码不含任何 LLM 客户端（已由 `scripts/test_fact_package.py` 静态+动态双重验证） |
| 结束时输出实际用量 | `CallStats` 汇总 tokens、重试次数与费用 |

### 全量前的一个"意料之中但要说清楚"的现象：方面分析全部不出结论

实测：当前 57 个景点的事实包里，**没有任何一个方面达到"出结论"的门槛**
（方面样本量分布为 1×25、2×5、3×4、5×1，全部 < 10）。

**这不是 bug，而是两件事叠加的必然结果，答辩时应主动说明：**

| 原因 | 说明 |
|---|---|
| ① 方面标签只来自 deepseek 路径 | `mllib` 基线（47,110 行）**不带方面标签**；所以"某景点 1,033 条情感样本"并不等于"1,033 条带方面"。 |
| ② 真实语义结果只有 31 条 | 目前只跑过 31 次真实调用，分摊到 57 个景点后，单个方面的样本自然远小于 10。 |

于是 BR-04（"方面样本 <10 条 ⇒ 只展示样本量、不出结论"）**被正确执行**：
系统没有编造倾向，而是如实写"样本不足（<10 条），不纳入评价"。
**全量运行完成后，方面样本会按数量级增长，大多数方面将变得可出结论。**

> 换个说法（答辩可直接用）：
> "现在看到'方面不出结论'，恰恰说明**证据不足时系统不硬下结论**。
> 这条规则在数据充足时不妨碍结论，在数据不足时能防止编造——
> 这正是设计里 BR-04 想要的效果。"

> **待补跑 1 条（如实记录）**：`comment_id = 73603914` 原有一条真实 API 结果，
> 在开发期的"写库失败兜底测试"首版中被测试数据覆盖（该测试当时用写死的样例内容，
> 直接 upsert 到了真实评论上），其原有方面行一并被删除。
> 由于原始返回值不可复原，已**把该条的伪造结果全部删除**，使其回到"待处理"状态：
> 它现在是 47,702 条待调用中的一条，**下次全量运行会被自动重新分析**，
> 恢复后真实 API 完成数将回到 32 条。此过程**未额外调用任何 API**。
> 相关测试已改为"快照 → 断言 → 逐字段还原 + 前后行数一致"，
> 从机制上杜绝再次发生（见 `scripts/test_write_recovery.py`）。
