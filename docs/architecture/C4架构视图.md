### 1.1 架构总原则

> **数据负责事实，DeepSeek 负责语义理解与自然语言解释。**

由此推导出三条架构约束，贯穿全部三层视图：

| # | 约束 | 体现方式 |
|---|---|---|
| A1 | **统计与对比结果一律由系统按既定规则计算**，不由模型生成 | 所有指标表（`stat_*`）由 Spark／Python 产出；DeepSeek 的输出只写入 `*_report`、`comparison`、`qa_record` 等"解释类"表 |
| A2 | **离线批处理与在线服务分离**，在线请求不触发昂贵的模型调用与批处理作业 | 批处理由 Python／Spark 脚本执行；Web 服务只读 MySQL，生成类内容读取已落库结果 |
| A3 | **模型调用的输入必须是被裁剪过的事实**，不是原始数据全集 | 事实包由系统组装；问答只传检索到的结构化结果，不传大量原始评论 |

### 1.2 技术栈红线：本架构中禁止出现的组件

**禁止使用以下任何组件**：Flume；Kafka；Spark Streaming；Flink；Hadoop 集群；Hive；HBase；Redis；Docker；Kubernetes；Elasticsearch；消息队列；微服务拆分；向量数据库；RAG；Agent。

**理由**：数据为一次性采集的历史评论静态快照（59,033 条），无实时数据源、无高并发需求；引入上述组件不产生业务价值，只会增加部署复杂度与答辩风险。本架构采用**单机进程 + 单库**的形态。

## 4. 关键架构决策记录（ADR）

| # | 决策 | 备选方案 | 选择理由 |
|---|---|---|---|
| ADR-1 | 采用**批处理 + 只读 Web** 的两段式，而非请求时实时调用大模型 | 在 Web 请求中直接调用 DeepSeek | ① 模型调用耗时 10–30 秒，无法满足 NR-P-01（≤3 秒）；② 重复访问会重复计费，违反 CC-2；③ 请求期失败会直接暴露给用户。批处理落库后可反复读取、结果稳定可复现 |
| ADR-2 | 语义结果与统计结果**分表存储**，不混在一张宽表 | 单张"评论全字段宽表" | ① 语义结果存在**多方法**（DeepSeek／MLlib／词典法）需并列对比，宽表无法表达；② 批处理需支持断点续跑与部分重跑，分表可按需重算 |
| ADR-3 | 智能问答**不做向量检索**，采用"结构化检索 + 事实拼装" | RAG + 向量数据库 | ① 数据是结构化统计结果而非长文档，直接 SQL 即可精确定位；② 系统需回答"有多少条负面评论"这类**数值精确**问题，向量检索无法保证；③ 无 GPU、无向量库部署条件（技术栈红线） |
| ADR-4 | Spark 与 Python 职责**按数据形态划分**，不按功能划分 | 全部用 Python／全部用 Spark | ① Spark 承担 59,033 条的全量聚合与 MLlib／LDA 训练（体现分布式计算能力）；② Python 承担行级清洗与 HTTP 调用大模型（灵活、便于断点续跑）。二者通过 MySQL 解耦，职责不重叠 |
| ADR-5 | 不引入缓存中间件 | Redis | 单机、10–20 并发（NR-C-04），MySQL 查询加索引即可满足 ≤2 秒/≤3 秒指标；"缓存"通过**结果落库**实现（生成类结果不重复调用模型），比引入 Redis 更符合成本控制目标 |
| ADR-6 | 景点级字段拆为独立维表 | 保留在评论表中 | 地址／开放时间／官方电话／景点介绍在同一景点内完全重复，留在评论表会造成冗余，且建模时易被误当特征（BR-09 明确禁止） |
